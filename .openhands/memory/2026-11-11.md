## BUG encontrado (o teste 6 pegou)

O handler mandava figurinha ANIMADA como `type: 'video'` (para o `sendSticker`).
O decoder de WebP do **ffmpeg IGNORA os chunks ANIM/ANMF** (0 frames) — então
figurinha animada falharia. Correção: `type: 'image'` SEMPRE (o mesmo caminho do
`!take`). Como a figurinha JÁ é webp, o `sendSticker` reconhece o RIFF/WEBP e
devolve o buffer direto — **sem ffmpeg**. Testado sem ffmpeg no PATH.

## `!pinsta` + `!keyig` — cookie do Instagram (o endpoint anônimo MORREU)

### O diagnóstico (medido, não suposto)
O `!pinsta` "só dava erro" porque o Instagram **desligou o caminho anônimo**:
- `www.instagram.com/api/v1/users/web_profile_info/?username=X` → **404** (HTML de erro)
- `i.instagram.com/api/v1/users/web_profile_info/` → **404**
- `api/v1/users/X/info/` anônimo → **400** "something went wrong"
- `?__a=1&__d=dis` → **201 vazio**
- O download de reel anônimo (`igdl.dl`) → "Postagem não encontrada"

Ou seja: não era bug do bot; o Instagram passou a exigir login.

### A correção
- **`dados/src/utils/instagramCookies.js`** (novo, puro): lê o `sessionid` de
  `data/instagram/cookies.txt` (Netscape, igual ao YouTube) OU
  `data/instagram/sessionid.txt` (gravado pelo `!keyig`); env `IG_COOKIES_FILE` /
  `IG_COOKIES_DIR`. `extrairSessionId` aceita os dois formatos.
- **`socialProfile.js`**: com sessão → API privada autenticada (devolve o
  **CABEÇALHO** de qualquer perfil, inclusive **PRIVADO**: foto, nome, seguidores,
  seguindo); sem sessão → tenta o anônimo e, falhando, orienta o `!keyig`.
  Seam de teste `IG_API_BASE`.
- **`!keyig`** (`keyinstagram`/`igkey`): só o dono. Sem arg = painel + tutorial;
  `!keyig <sessionid>` grava; `!keyig limpar` apaga. Nunca mostra o valor inteiro.
- `menudono` (categoria **COOKIES / REDES SOCIAIS**, baseline 175→177) + `blockPv`.
- `.gitignore`: `data/instagram/` e `*.instagram-cookies.txt` (o cookie = a conta).

### O limite honesto (dito ao dono)
A conta **NÃO** desbloqueia conteúdo de perfil privado (posts/stories) — isso só
com "seguir e ser aceito". O que ela libera é o **cabeçalho** de qualquer perfil.
O cookie também **expira** e a conta pode ser **bloqueada** por automação.

## `!pinsta` — a ROTA estava errada (2ª rodada) + STORIES

### O "Perfil não encontrado" tinha DUAS causas
1. **A rota.** Eu usei o `web_profile_info`, que hoje devolve **404 "Page Not
   Found"** para QUALQUER usuário — mesmo com TODOS os headers do navegador
   (LSD, csrf, referer, X-IG-App-ID). A rota que o app/instagrapi usam é
   **`users/<u>/usernameinfo/`**. Confirmação: o **yt-dlp desativou** o extractor
   de perfil (`InstagramUserIE._WORKING = False`) — não há caminho público.
2. **O 404 era tratado como "não existe".** O `web_profile_info` dá 404 para
   TUDO, então `@l.szzy` (usuário real) virava "não encontrado".

**Correção**: cadeia de rotas `usernameinfo → web_profile_info → info`; 404 numa
tenta a próxima, 401/403/429 (sessão) para na hora; todas 404 → "não encontrado";
aceita o formato das duas (`user` direto OU `data.user`). Sem sessão, o bot
**orienta** o `!keyig` em vez de tentar (sem cookie o IG responde 400/403/404
para qualquer um — não dá para distinguir). Seam de teste `IG_API_BASE` troca só
o HOST (a cadeia continua).

### STORIES (`igdl.dlStories`)
- **Story exige login** — é a mesma regra do perfil (o `sessionid` do `!keyig`).
- Fluxo: `/stories/<user>[/<id>]` → `usernameinfo` (pega o `pk`) →
  `feed/reels_media/?reel_ids=<pk>` (o endpoint que o yt-dlp usa). Devolve foto E
  vídeo no formato `{ type, url, mime }` que o `!instagram` já envia.
- O `!instagram` detecta `/stories/` e chama `dlStories`; o resto (post/reel)

- `extrairStory` aceita `/stories/<user>` (todos) e `/stories/<user>/<id>`

## Instagram — a sessão é RECUSADA (diagnóstico definitivo)

O `!keyig testar` mostrou (com os headers completos já aplicados):
```
current_user (app): HTTP 200 ❌ SESSÃO INVÁLIDA
usernameinfo (app): HTTP 200 ⚠️ status:fail
web_profile_info (web): HTTP 429
info (app): HTTP 400 ⚠️ status:fail
```

**Leitura**: os headers NÃO eram a causa (o 200+fail persistiu com os ~31
headers). O `current_user` — que devolve a conta logada quando o sessionid
presta — diz **recusada**. Ou seja: **o Instagram não aceita a sessão**, e o
`429` (rate limit) na rota web aponta **IP flag**.

Duas causas possíveis, correções opostas:
1. **cookie inválido/expirado** → renovar o cookie;
2. **IP do servidor bloqueado** (datacenter/VPS) → nenhum cookie resolve.

O diagnóstico agora mostra **o IP do servidor** e testa o `current_user` nas
**duas casas** (app e web) — para separar as duas.

### O que NÃO fazer (decisão registrada)
Não vale "engenharia reversa do Instagram": o protocolo privado já está
documentado em implementações mantidas (instagrapi, aichemy). O que resta **não
é protocolo** — é a decisão do servidor (IP/sessão). RE não muda isso.
